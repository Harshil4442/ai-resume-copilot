# Detached provider-cost retention (isolated v2 development)

This patch repairs a reproduced gap on source `49abdeb06a987e23b9484cb3fd6437a2ac6d5b73`. The actual account-deletion handler erased both `AnalysisRun` and `ModelCallEvent` for admitted `reserved`, `outcome_unknown`, and `usage_unavailable` attempts. Each synthetic case lost a 1,267 USD-micro hold, and a late valid usage callback raised `NoResultFound`. Historical evidence remains in the separate reproduction artifacts; those tests assert the old defect and are not acceptance tests for this patch.

One `ModelCostLiability` row is committed atomically with each existing attempt reservation before SDK construction or network work. It has no customer/run/event foreign key. Its financial group and liability IDs are freshly random accounting surrogates; neither derives from a user, client request, input fingerprint, resume, or original run ID. Deletion removes all ordinary run/event/payload rows without touching this ledger. Routine model-telemetry retention cannot delete its holds.

These are pseudonymous financial records, not proof of complete anonymization: active run/event links, backups, timestamps, provider and model can correlate them with prior activity. The exact retained field whitelist is: random liability/group IDs; attempt number; provider and configured model; SHA-256 of the operator-configured endpoint (not the URL); currency `USD`; price/configuration version, integer input/output rates, input/output bounds, output-limit parameter, estimator version, operation/admission policy versions, and authorized numerical ceiling; numerical input estimate; immutable original reservation; nullable settled estimate and numeric returned input/output tokens; bounded usage provenance and cost state; creation/settlement timestamps. No user/email/subject/customer identifier, original run/event/request/idempotency key, prompt version, resume, prompt, input or result payload, credential, raw response, API URL, price URL, provider exception, latency, cache or fallback metadata is retained here.

An unsettled row's held amount is its entire original reservation. A settled row's held amount is zero; the original reservation remains audit evidence. Missing or invalid usage, errors and crashes retain the entire hold. Settlement uses the frozen numerical quote and validates trusted usage exactly as before, so it remains a usage-based estimate rather than a provider invoice cap. Changed policy cannot reprice a past attempt. Settled evidence is retained too; a future operator-reviewed financial retention policy is outside this patch.

The existing PostgreSQL transaction-scoped account-lifetime advisory lock is reused for analysis creation, synchronous billable creation, model admission/settlement, and account erasure. Erasure acquires it before mutations and locks existing analysis runs in sorted order before deleting model events or taking the owner lock. Admission rechecks the owned run and owner under that guard; a stale budget cannot admit another provider call after deletion. These short transactions finish before caller SDK/network work. SQLite fixtures do not prove concurrency.

The trusted current-call closure retains only an in-memory event-to-financial binding. After erasure it can lock and settle that detached liability once, without requiring or recreating a SQL owner/run/event. Duplicate completion/error callbacks cannot release a hold twice. A newly constructed budget cannot recover a deleted account or discover liabilities by deleted IDs. Existing trusted active-owner worker reconciliation remains available through its owned run/event binding. No detached-liability reconciliation HTTP endpoint, callback loader, provider-invoice ingestion, or externally asserted usage is added.

The unpromoted `0010` migration adds the ledger and live-row links. Legacy `0009` history remains unquoted, with no invented price or retrospective reservation. An empty-liability migration can downgrade/upgrade. Any retained liability prevents downgrade before destructive work, including settled rows, because `0009` cannot represent the retained financial evidence. The separate old-writer quiescence/fenced cutover remains required; serving `0009`, deployment flags, resources and production are unchanged.

Acceptance requires real disposable-PostgreSQL interleavings for admission-before-erasure, erasure-before-admission, both orders of settlement-versus-erasure, creation-versus-erasure, concurrent duplicate late settlement and transaction rollback. It also requires the financial field whitelist, independent telemetry pruning, unknown/crash retention, immutable quotes, active-owner isolation and migration refusal/empty round-trip. This document records a local implementation boundary, not deployed acceptance, invoice reconciliation, independent-SQL-restore protection or a production spending guarantee.

The superseded v1 patch (`cc16932f10626ff8e6ef9d4bed1ee286f40dc02a2b82bd149d9daee96615fa1d`) passed its original bounded checks but independent actual-PostgreSQL review reproduced two result-write deadlocks: tailoring acquired Resume before erasure-held Run, and legacy enrichment flushed Resume before its final-only advisory guard. Those failing artifacts remain historical evidence; they are not cleared by the earlier 96-case run.

V2 adds the explicit `begin_result_commit` seam after all provider and rendering/retry work, before customer-result row locks, mutations or flush. Under `no_autoflush`, it acquires the existing lifetime advisory guard, checks the live owner and freshly reads/locks the run without replacing staged ORM attributes. Normal result writes reject cancelled/terminal runs. Tailoring, enhanced/basic job matches, interview telemetry, actual upload enrichment and worker result/product-unit completion/failure enter this boundary. The guard remains until the caller commits or rolls back that short transaction. It is not a global session hook and cannot protect a new caller that flushes result rows before invoking the seam. Audited pure legacy response paths have no result-row mutation and enter guarded final unit/run settlement after their SDK/render work finishes. No SDK, rendering, provider retry, notification delivery or dispatch call occurs inside the result-write transaction; notification enqueue is local SQL only.

The new actual-PostgreSQL regressions place barriers before or immediately after the result guard, never after a conflicting unguarded Resume lock. They exercise both serialization orders through the actual tailoring worker (real source extraction, validation and DOCX rendering; one synthetic admitted provider response) and actual asynchronous upload-enrichment handler (synthetic extraction/provider result; real caller Resume flush and unit/run settlement). They also verify staged-memory `no_autoflush` protection, fresh cancellation checks, no result writes after erasure, no provider re-execution and independent financial cost retention.
