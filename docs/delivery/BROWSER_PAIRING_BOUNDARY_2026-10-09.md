# Browser-first device pairing boundary — read-only review, 9 October 2026

Recommendation: implement a **pairing-only identity boundary**, with a default unavailable production adapter. A paired key can identify a candidate-owned browser installation; it cannot approve a job, authorize an employer origin, download arbitrary files, fill a field, submit, release an opening claim or settle credits. The first deployable boundary requires independently retained subject/device lifecycle state and genuine candidate authentication. Adding a SQL device table or changing the fixture transport URL is insufficient.

## 2. Stable subject lifecycle must precede production pairing

Add an opaque random `subject_uuid` for each account lifetime, mirrored in SQL but owned by an independent subject registry. The registry binds the subject to a verified account-registration event and current authentication generation; deletion is monotonic. Never derive it from email/numeric ID, create a replacement automatically when a SQL mapping is missing, or attach an old deleted subject because a restored row/queue says it is active.

A recreated account receives a new UUID even if it uses the same email/provider principal; old device IDs, subject tombstones and opening claims remain attached to the old lifetime. A same-account SQL restore retains the UUID and must reapply independent deletion/authentication-generation denials before access. Missing/contradictory mapping, unexpected authority incarnation or an unreplayed restore stays closed. Restored SQL and outbox messages cannot create registry subjects, pair devices or register approval.

Resolve the initial legacy-account bootstrap before any production enablement: existing accounts have no independent historical subject evidence. A reviewed baseline/backfill and fresh candidate authentication can establish a declared start point; they cannot prove earlier unrecorded deletion history. Do not label opportunistic login-time UUID generation restore-safe. Also decide how genuine account recreation interacts with historical repeat-application policy; a new account lifetime is not proof of a different human, and email-based fuzzy merging is not an acceptable hidden workaround.

For Google, independently bind the verified issuer + provider subject to an explicit account lifetime; email is a display/contact attribute. For password accounts, bind a server-verified recent authentication event to that same independently registered lifetime. Existing general bearer tokens have no trustworthy recent-authentication/authentication-generation evidence; do not treat `exp` or possession of one as recent reauthentication.

## 3. Minimal two-party, single-use pairing flow

Start with one active candidate account per extension installation; switching accounts requires an explicit disconnect/re-pair. No bulk enrollment, QR-to-arbitrary-device enrollment, device recovery by email, or employer permission is part of this slice.

1. **Popup starts pairing:** create/use its local non-extractable key; request a short-lived challenge from a fixed trusted TLS authority origin. Send only public JWK/fingerprint and protocol/release identity. Validate the public key and signature; the server allocates the canonical device ID. A client-chosen installation ID is not ownership.
2. **Candidate confirms on HireWiz:** open only the fixed official HireWiz pairing page with an opaque request ID, never a bearer token, pairing secret, password or resume in the URL. Show the current account, device fingerprint and “connect this browser only; no job will be filled.” Require fresh password/provider authentication for first pairing, rotation or account switch. A same-origin, CSRF-protected explicit confirmation consumes a candidate challenge bound to this exact request/key/subject/epoch.
3. **Device completes:** a fresh device-signed challenge binds the candidate-confirmed subject and pairing digest. The independent authority atomically rechecks active subject, authentication generation, epoch, existing key ownership and both unconsumed challenges, then creates the immutable owner/key enrollment and consumes the request. Neither a candidate session alone nor a device signature alone can complete pairing. Serialize device ownership with revoke/delete operations; never reassign an active/revoked device ID to another subject.
4. **Receipt, not capability:** return a short issuer-signed `device_claim` only after confirmed independent commit and verified journal receipt. Claim identifies owner/key/generation; it grants no disclosure. Lost/duplicate completion is status-only; a separate fresh signed claim-refresh request may identify the current device after a current registry check, but cannot replay an action or refresh its deadline.

Suggested fixed upper bounds: pairing request ≤120 seconds, candidate-confirmation challenge ≤60 seconds and ≤request expiry, device possession challenge ≤10 seconds, claims ≤5 minutes. These are proposed policy values to freeze/test, not current production settings. Rate-limit unauthenticated challenge creation and confirmation attempts. Store nonce hashes and bounded metadata; never allow an arbitrary remote URL proxy.

## 4. Exact immutable protocol inputs

All server-derived fields below are compared to independent current state, not accepted as client identity declarations. Use domain-separated v2 canonical JSON, exact Unicode scalar strings/no silent normalization, ASCII schema keys, typed string/boolean values, strict JS-safe numeric fields, UUID strings and decimal **string** storage generations. Use independently verified Python/WebCrypto signature and hash vectors; the v1 fixture's generic numeric canonicalizer must not silently become the production v2 protocol.

## 5. Rotation, unpair, deletion and account switch

- **Device rotation:** fresh candidate confirmation and new-key possession; old device/key-generation tombstone verified before activating a new enrollment. Preserve previous opening/attempt/unknown evidence. Do not overwrite a key and reinterpret pending commands under it. Lost key means new pairing, not recovery of old may-act proofs.
- **Unpair:** candidate-owned or current-device signed revocation, serialized against pairing completion/claim refresh/begin. Persist the independent deny and protected journal before success. An ambiguous result is pending revocation/status-only; no cached offline claim remains sufficient. Already-begun autosaves cannot be recalled.
- **Sign out/switch account:** immediately clear claims/review/file/answer buffers and stop local work; preserve uncertain checkpoints. Server-side device command-session invalidation must be independently verified, or UI reports local stop plus pending remote invalidation. Pairing can remain registered for its original subject, but cannot silently reconnect to another account. Use a new enrollment/key namespace on switch and retain old tombstones/checkpoints. The current website remounts queries/page drafts on owner changes; this does not clear the standalone extension. [web boundary](../../frontend/components/SessionProviderWrapper.tsx).
- **Deletion:** journal + subject/device/authentication-generation revocation first, SQL erasure and generation-bound GCS cleanup afterward. If independent authority is unavailable, future browser action is already denied; record/retry a durable deletion intent and distinguish blocked execution from incomplete erasure. Do not acknowledge complete revocation from SQL-only success. Recreate neither deleted profile nor approval payload during reconciliation.

A Chrome `permissions` removal or current tab/document/navigation change separately stops future steps; it is not a server tombstone. Request exact employer-origin access only when the candidate selects a permitted job, never `<all_urls>` or a vendor-wide blanket grant. Tenant/route/adapter checks remain necessary where many tenants share an ATS origin. CAPTCHA/login/MFA/unsupported/conditional fields pause; final submit and file upload remain candidate-controlled.

## 6. Production authority dependencies and smallest next slice

The recovery adapter review already identifies the prerequisite orchestration: buffered transactional registry reads/writes, independent generation-bound journal receipts, status-only handling of ambiguous commits, partitioned tombstones/claims, pinned authority identity and closed replay cut. [adapter prerequisites](../../docs/delivery/PRODUCTION_RECOVERY_ADAPTER_REVIEW_2026-10-08.md). Pairing must use the same subject/device records as deletion and action begin, not a separate stale SQL registry. Journal and registry are not one cross-service transaction; missing/unverified receipts stay unavailable and orphan revocations replay as denies.

Smallest useful development slice: new `pairing_contracts.py` / `pairing_service.py` beside the recovery core, a separate trusted-candidate assertion verifier boundary, and focused synthetic registry/crypto/process tests. Add independent subject/device generation/tombstone records and single-use challenges; preserve v1/v2 sequence tests. Leave the production store and HTTP/browser transport unavailable until its registry/journal/authentication guarantees are implemented and reviewed. Then add a narrowly authenticated web confirmation + signed-device transport with production disabled; test it against a synthetic portal before considering a tenant adapter. No browser host grant or employer enrollment is needed to prove pairing identity.

A production release additionally needs: a reviewed legacy subject bootstrap/migration, identity-principal linking/recent-auth policy, deleted-subject authentication denial, protected journal retention and IAM separation, actual registry concurrency/ambiguity/replay proof, issuer-signing and key-rotation trust, exact allowed extension identity/distribution policy, and same-owner sealed-package/v2 bridge tests. These are outstanding dependencies, not properties provided by the local SQLite fixture. No cloud resources or retention locks are proposed as automatic implementation side effects.

## 7. Acceptance cases and unresolved decisions

Minimum focused proofs: competing owners for one pairing/key, two devices for one pairing, altered public key/request/audience/release, expiry and one-use candidate/device challenges, stale/forged auth generations, wrong subject/session, rotation/unpair/delete racing completion/refresh, simultaneous account switch, signature format and Node/Python canonical vectors, commit-before-reply loss/restart, journal-only pairing/revocation cuts, missing or restored subject mapping, application-only restore retaining deletion/device denies, and closed authority replay with missing partitions. Assert no job/field permission emerges from a successful pairing or duplicate receipt. Later actual-Chrome tests must cover worker restart, retained unknown checkpoints, profile/account switch, permission revocation, untrusted page messages and absence of exported HireWiz/employer credentials.

Unresolved before enablement: legacy-account bootstrap and independent registration provenance; password/provider recent-authentication semantics and principal linking; authority/issuer/IAM/retention/residency policies; extension signing/distribution identity; first tenant's independently approved fill permission and exact form adapter; admission-budget treatment of fill/autosave versus final submission; repeat-application policy after genuine account recreation; artifact size mismatch (backend allows 10 MB, local v2/extension allow 5 MB); and candidate-review UX bridging web authentication to the local popup. Do not hide these with inferred grants, silent file conversion, SQL/Redis fallback, reconstructed permits, an “Applied” label, or credit settlement from local filled observations.
