# Production recovery adapter review — 8 October 2026

The disabled core is a useful one-store safety model. `AuthorityStore.transact(callback)` can support a Firestore implementation with an explicit buffered/retry contract; it does not currently express the independent GCS journal protocol or a production restore barrier. Those require a small orchestration boundary. Registry and journal are two stores with no shared atomic commit. Production remains disabled; browser filling is the intended first capability, with upload/final submission manual and no automatic charge settlement.

Reviewed the root worktree recovery contracts/store/service and `docs/delivery/RECOVERY_FOUNDATION_PLAN.md`. The reported 630 backend tests and local SQLite process/restore tests do not establish cloud IAM, protected retention, authority rollback detection or physical browser egress safety. No credentials, cloud resources, employer endpoints or production operations were accessed.

## Actionable blockers and minimum changes

1. **Specify a buffered Firestore transaction facade.** `_now()` writes `clock/observed` before `_binding()` reads device/grant records; event append and immutable puts also interleave reads and writes. A direct SDK wrapper fails Firestore's ordering requirement. Buffer every mutation locally, serve read-your-staged-writes from the overlay, record/read the original transactional document version when needed for immutability or absence checks, then queue all SDK writes only after the callback and validation finish. Rebuild the overlay and read set on each SDK retry. Never use an ordinary read outside the transaction to establish claim absence, current revocation or ownership. Firestore retries callbacks, requires reads before writes, and its native reads do not see preceding staged transaction writes. [Transaction rules](https://firebase.google.com/docs/firestore/manage-data/transactions), [isolation rules](https://firebase.google.com/docs/firestore/transaction-data-contention#isolation_within_a_transaction).

2. **Keep transaction retries separate from logical request retries.** Pure UUID/time generation inside an aborted Firestore attempt is not intrinsically unsafe: only the successful attempt's state/result may escape. It is nevertheless unsuitable as the identity of an already-written GCS intent. Allocate a stable, bounded operation ID and created-record IDs once outside SDK retries; bind the operation ID to exact authenticated scope and intent digest. A different payload under the same ID is a conflict. Fresh time checks still run on every retry; do not freeze an early timestamp that could authorize an expired action. Preserve the original decision expiry and postcommit stale/invalid-clock suppression. No callback may sign/send a browser command, write GCS, notify a client, or mutate external application state.

3. **Add typed journal orchestration, rather than hiding cross-store work in `transact`.** The smallest interface addition is an immutable operation context containing operation ID, kind, authority/incarnation, partition, sealed binding digest and a verified `JournalReceipt(bucket, object, generation, content_sha256)`. A production-only coordinator validates the operation, creates/verifies its deterministic write-once intent, then invokes the pure Firestore transaction with that context. The transaction rechecks current authority and stores the exact receipt alongside the begin/claim or tombstone. Both verified journal receipt and confirmed Firestore begin must precede any authorizing reply. Keep `transact` documented as Firestore-only atomicity; its contract must distinguish confirmed commit from unavailable/ambiguous outcome. A completion marker can improve audit/replay classification, but replay cannot assume its absence proves no begin.

   For a begin, the protected intent needs enough data to reconstruct a conservative permanent opening claim after authority rollback: operation/permit/attempt identity, stable subject/opening key, exact binding digest, authority/incarnation/epoch and protocol version. For revocation it needs the complete minimal deny scope/revision. Do not put raw answers, file contents or cookies in the journal. Journal-only begins become possible disclosure; journal-only revocations become pending denials during recovery. This deliberately sacrifices availability after some crashes. Do not acknowledge a completed revocation while either durable write is unverified. The live race boundary remains the Firestore transaction, not the earlier intent upload.

4. **Handle ambiguity without rebuilding permission.** An RPC deadline/error can occur after a state-changing operation has succeeded. After an ambiguous Firestore commit, discard the computed may-act result; exact operation lookup may reconcile status, but cannot remint or return a proof. Only definite aborted transaction attempts may be retried for a winning result. Pin/test the SDK retry policy rather than assuming every exception means rollback. [Google RPC deadline semantics](https://docs.cloud.google.com/tasks/docs/reference/rpc/google.rpc#code). Current duplicate-begin behavior is a useful foundation; retain it through HTTP and signing layers.

5. **Define an independently retained, fenced replay cut.** The current `barrier()` only reports the local authority head. Restoring that authority also restores the head, so it is not evidence against its own rollback. A production open operation needs a protected replay manifest generated while writers/executors are fenced: authority identity, new incarnation/epoch, exact destination database resource, partition inventory/high-water marks, journal object generations/digests, deny/claim projection coverage, unresolved-intent inventory and evidence horizon. Opening must verify that manifest and exact projected state, rather than accept a caller-supplied evidence label. Cloud Storage object/list reads are strongly consistent, but separate object operations and batches are not one transaction; an unfenced multi-page listing is not a sealed replay cut. [Storage consistency and atomicity](https://docs.cloud.google.com/storage/docs/consistency).

   Firestore backup restoration normally targets a new database. The adapter must pin project/database identity and reject unexpected destinations or copied `OPEN` state. [Firestore restoration](https://docs.cloud.google.com/firestore/native/docs/backups#restore_data_from_a_database_backup). The plan explicitly excludes unannounced restores outside its enforced procedure. Keep that limit: an epoch/head stored only in the restored Firestore database cannot detect such rollback. If that threat enters scope, an externally pinned witness plus checks at every authorizing path is additional work, not a property of this interface.

6. **Partition local proof machinery before production scale claims.** Do not translate global `clock/observed` and one global journal head into documents written on every tenant action. Use stable subject/authority partitions for deny/clock/event progress, exact opening-claim documents for opening ownership, and a rarely changed global epoch/control record read by each transaction. Subject deletion and begin must share the affected subject record; narrower partitioning must not separate that race. Partition journal chains/checkpoints and replay a protected partition manifest when closed. Runtime validation checks bounded affected projections and receipts; the fixture's full historical journal scan belongs to closed replay/drills, not every production begin. Define/test clock skew across replicas without substituting a stale cached time. Keep hashes/scattered Firestore document IDs; avoid a sequential global event collection/index hotspot. Exact single-document capacity depends on workload and requires load tests; no fixed production throughput follows from the local tests. [Firestore scale guidance](https://docs.cloud.google.com/firestore/native/docs/best-practices).

7. **Make server derivation and browser guarantees explicit.** An authenticated actor struct or a client-declared binding is not authentication. Production adapters must derive subject/device/key/executor and exact destination/form/field/value/file semantics from authenticated enrollment, the sealed server package and the reviewed adapter version. The browser reports current document observations; it cannot choose new approved semantics. Each step needs current authority, exact document/form checks and a fixed freshness deadline immediately before mutation. Chrome may terminate extension service workers and loses their global state, so in-progress/unknown checkpoints persist and never restore a cached may-act token. [Worker lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle). Chrome supports targeting a specific document ID, which helps prevent frame/navigation substitution but does not fence all user-local egress. [Document injection targets](https://developer.chrome.com/docs/extensions/reference/api/scripting#type-InjectionTarget). Already-begun fill/input events may autosave; cancellation cannot promise recall. Local filled observations establish neither employer completion nor charge settlement.

## Journal protection and tombstone rules

Use generation-zero writes at deterministic operation paths. On 412 or an uncertain upload, retrieve the exact object generation and compare its canonical bytes/digest; a matching object permits idempotent journal reconciliation, while a mismatch is a hard conflict. A missing/unreadable object is not successful journaling. `ifGenerationMatch=0` checks absence of a live object, not an eternal never-used name, so protect generations and runtime permissions as well. [Generation preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions).

Bucket retention protects object data for its configured duration; a locked policy cannot be reduced, but editable object metadata is not protected. Hash and replay the content at its recorded generation, not mutable metadata. [Bucket Lock](https://docs.cloud.google.com/storage/docs/bucket-lock). The runtime writer needs create plus narrowly scoped read/verification access; Object Creator alone cannot read, delete or overwrite objects. Keep retention/IAM administrators separate and deny runtime delete/update/restore permissions. [Storage IAM roles](https://docs.cloud.google.com/storage/docs/access-control/iam-roles#standard-roles). IAM removal is eventually consistent, so it is not an immediate physical fencing primitive. [Access consistency](https://docs.cloud.google.com/storage/docs/consistency#eventually_consistent_operations).

Never TTL an unresolved opening claim or deny because a permit expired. Union tombstones across replay, preserve old revisions when registering new ones, and never reuse a deleted subject UUID. Compaction requires a protected checkpoint covering the complete prior prefix and all still-active denies/claims. Reject backups older than the declared retained-evidence horizon; finite journal retention cannot justify an indefinite rollback claim. Retention locking and resource provisioning are later reviewed infrastructure actions, not part of this review.

## Failure handling table

| Cut or fault | Authorizing result | Required retained/recovery behavior |
| --- | --- | --- |
| Invalid auth, sealed package, device or reviewed adapter | None | Reject before journaling candidate disclosure intent; no client-string fallback |
| Definite Firestore ABORTED/contention retry | Only a later confirmed unique winner | Recreate the buffer; stable operation/intent identity; fresh deadline checks |
| Retry exhaustion or expired/decreasing clock | None | Bounded unavailable/paused response; never use a prior attempt's result |
| GCS upload times out or returns 412 | None until exact receipt is verified | Same bytes/generation reconcile; mismatch denies; no assumption that timeout means absence |
| Intent exists, process dies before Firestore begin | None | Retain conservative possible-disclosure intent; recovery cannot create a replacement opening attempt |
| Firestore begin commits, response is lost/cancelled | None on retry | Claim remains; status-only reconciliation; no recreated decision/signature |
| Confirmed begin reply arrives after its fixed deadline | None | Burned begin remains; never restart the decision lifetime |
| Revocation intent succeeds, registry/SQL update fails | No successful revocation acknowledgement | Pending deny is replayable; blocked state persists once applied; retry erasure without recreating PII |
| Begin and revoke race | Firestore winner defines boundary | Revoke-first denies begin; begin-first retains possible disclosure and cannot be recalled |
| Application-only restore | Old work cannot regain permission | Retained authority denies/claims plus new epoch; restore admission usage without inventing refunds |
| Authority restored, journal gap/mismatched generation, incomplete partition cut | None | Stay CLOSED; reject opening until complete externally retained replay evidence exists |
| Browser worker restart/offline/navigation or ambiguous mutation | No further automatic step | Durable unknown/in-progress checkpoint; no proof replay or automatic submission |
