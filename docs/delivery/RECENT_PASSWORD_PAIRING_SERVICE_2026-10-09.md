# Recent-password pairing authentication service — isolated implementation

This stage implements password reauthentication and connects it to the actual identity-only `PairingService` confirmation/revocation transactions. It does not enable a route, production factory, account-registration writer, independent authentication session, employer action or automatic submission. All behavioral evidence below uses synthetic candidates, a real local SQL password row, real PBKDF2 verification, real ES256 test signatures and a separate journaled SQLite authority fixture. The fixture is not a production recovery store.

## Implemented service

`backend/app/domains/recovery/password_reauth.py` contains:

- `PasswordReauthRequest`: an exact, bounded protocol-2 body. Password and nonce use `SecretStr` and are excluded from the representation. Extra identity, bearer, issuer, generation and clock fields are rejected. Passwords preserve their exact characters and whitespace and accept at most 1,024 UTF-8 bytes. The nonce must be a canonical 36-byte UUID string. Confirmation must be the actual Boolean `true`.
- `CandidateWebSession`: trusted server context containing a positive SQL candidate ID, independently registered account-binding UUID and independently retained session UUID. It is not a browser body or existing bearer claim. Current HireWiz bearer tokens do not supply the latter two fields.
- `SqlPasswordCredentials`: creates an owned credential-only connection pool from an explicitly injected trusted engine URL, opens a fresh short-lived session, and reads the current password hash with an actual native `sqlite3` or pinned `psycopg` cursor and fixed parameterized SQL. Credential results never pass through SQLAlchemy's ORM/result-row logger, including when DEBUG logging is enabled during the query. It closes the cursor/read session before running the existing password verifier; `close()` disposes its owned pool. A missing account, Google-only empty hash or stored hash exceeding 1,024 bytes cannot succeed. The operator must explicitly supply a valid dummy hash using the current password policy for missing-account verification; there is no credential or key bootstrap.
- `RegisteredPasswordIdentity`: a read-only adapter over an explicitly injected independent `AuthorityStore`. It requires exact account registration evidence, a current active subject lifetime, principal, authentication generation, an unexpired registered web session and the existing exact pairing-session record. It never creates a missing mapping or substitutes SQL/email for it. Independently retained account tombstones and subject revocations deny restored SQL identities.
- `PasswordReauthService`: verifies the password again, resolves current independent identity, checks the exact unconsumed challenge/nonce/operation/epoch, creates a server-owned `CandidateAssertion`, and calls an explicitly injected candidate-assertion signer. The assertion expires at the earlier of 60 seconds or the challenge deadline. The returned envelope must contain exactly the original assertion payload plus a signature. It sends a frozen private `CandidateDispatchCommand` to an explicitly injected trusted `CandidateAssertionDispatch` port. That command contains the canonical server context, bounded confirmation/revocation operation, exact challenge ID/nonce and assertion/signature; it contains no password, password hash or password-derived digest. The service accepts only an exact redacted result for the expected pairing/device and never returns the private command, assertion or envelope to the browser.
- `DirectPairingCandidateDispatch`: the explicit local-core adapter used by this stage's real-core tests. It invokes actual `confirm_candidate` or `revoke_device`; the existing pinned verifier still verifies the signature, and consumption atomically preserves all existing two-party/key-ownership restrictions. It has no implicit production fallback.
- `_IdentityFencedStore`: resolves the independent binding again inside every actual pairing read/consumption transaction. Closing a lifetime, rotating authentication generation, changing its owner binding or revoking its session during signing denies the consuming write. Credential reads and external signing occur outside authority locks. The trusted core's injected clock, verifier and allocator are preserved.

No password, password hash, raw nonce or bearer is passed into a persisted event or record. The existing protocol's pseudonymous `principal_sha256`, challenge nonce digest and assertion/context hashes remain necessary cryptographic bindings; they are not password hashes. The service does not log requests, envelopes or adapter errors. Public credential, ownership, proof and request-validation failures use `Recent password authentication failed`; infrastructure faults use `Recent password authentication is unavailable`. These labels do not claim timing equivalence between every failure.

The credential adapter supports only an absolute file-backed SQLite URL without query options, or `postgresql+psycopg`. It uses one connection, no overflow, and a configurable finite positive pool-wait budget of at most five seconds (default two). SQLite additionally has a busy timeout, progress deadline and `query_only`; PostgreSQL has native connect, statement, lock and idle-transaction timeouts and a read-only transaction. Integer native connect timeouts round up to a minimum of one second. These bounds do not establish a single end-to-end process or network deadline: driver initialization, per-host connection behavior and password verification have separate costs. The adapter copies the trusted URL, not opaque source-engine connection arguments/events; a production factory must review its dedicated TLS/connection policy. No global logging configuration is changed to protect credential results.

## Exact independent identity prerequisites

The reader requires operator-provisioned records with these exact fields. No provisioning API or automatic legacy backfill is added.

| Namespace/key | Required record/evidence |
| --- | --- |
| `pairing_account_bindings/<account_binding_id>` | `account_binding_id`, positive `candidate_id`, canonical `subject_uuid`, `principal_sha256`, `registration_event_id`; the named event must be `PASSWORD_ACCOUNT_BOUND` with the exact record minus `registration_event_id`. |
| `pairing_account_tombstones/<account_binding_id>` | Any retained row closes the mapping; absence is meaningful only within a confirmed complete independent authority. |
| `pairing_web_sessions/<session_id>` | `session_id`, `account_binding_id`, `subject_uuid`, `principal_sha256`, positive `auth_generation`, `registration_event_id`, positive strict `issued_at_ms`/`expires_at_ms`, actual `active: true`; the named event must be `PASSWORD_WEB_SESSION_CREATED` with the exact record minus `registration_event_id`. |
| Existing `subjects`, `revocations`, `pairing_sessions`, control and events | The core's current registration provenance, active lifetime, principal, generation, session and open authority/epoch checks continue to apply. |

The account-binding UUID must be created by a reviewed independent registration event for that account lifetime. A recreated account, including one using the same email, needs a new lifetime and binding. Password rotation, logout/session revocation and account erasure must update independently retained authentication-generation/session/tombstone state through reviewed lifecycle writers. Updating only a SQL password row does not establish this independent revocation protocol. The service correctly reads a changed SQL password, and independently rotated generation fences the assertion; it does not claim cross-store atomicity that has not been built.

The principal fingerprint and invocation binding must come from independently registered identity evidence, never from the password, password hash or a brute-forceable password-derived digest. Raw credentials remain confined to the short-lived password verifier call.

The default production authority and assertion adapters remain unavailable. The current GCP pairing command's namespace allowlist does not yet authorize these new identity-reader namespaces. Production integration therefore still requires exact namespace/IAM review and independently protected account/session provisioning and restore completeness. Passing application SQL, a local file, email, or an existing bearer as a substitute is unsupported.

The current `GcpPairingCoordinator` invokes the core only inside its restricted command scope. Calling a copied core's `confirm_candidate`/`revoke_device` directly outside `coordinator.execute` does not establish that scope and remains unavailable; copying the trusted core is not a native authorization bypass. A future trusted native implementation of `CandidateAssertionDispatch.consume(command)` must create/execute the exact server-side coordinator plan, connect independently acknowledged durable invocation admission and fresh fences, and run the identity recheck inside its authorized core transaction. Its plan/journal binding must omit raw passwords, password hashes and password-derived digests; raw nonce/envelope material must remain private while the retained intent uses reviewed exact digests. It must translate only a confirmed result and treat ambiguous admission/commit as status-only. This transport and reviewed native identity-reader namespaces are not implemented or proved by this local service stage.

## Replay and failure boundary

The existing pairing transaction is the durable single-use gate. A bounded process-local attempt latch additionally prevents simultaneous same-challenge signing and retries after signing or an uncertain authority response. Known failed read validation before signing releases that local slot. Confirmed success releases the slot because the challenge is durably consumed. Uncertain/signing failures retain the slot and fail closed when its configured positive capacity is exhausted; there is no automatic retry or eviction of uncertainty.

That latch is not durable invocation authorization across processes/restarts. The native bridge's independently acknowledged immutable invocation claim and complete restore/journal fences must be connected and verified before a production HTTP surface is enabled. A lost response requires status reconciliation; an assertion or claim is never reconstructed from this service's response. No source-side retry policy is expanded. A fresh password assertion does not grant an employer origin, form action, approval, artifact, service-credit reservation or financial authority.

Google recent authentication remains unsupported. `provider_reauth`, Google tokens and bearer values are rejected by this request contract. An eventual provider boundary must independently verify issuer/subject, recent provider authentication and the retained account lifetime; an ordinary Google login is insufficient.

## Future HTTP/BFF integration contract — not an enabled API

1. Add an authenticated **web-only** same-origin candidate surface, for example `POST /api/backend/pairing/password-reauth`. Before JSON parsing, reject bodies over 16 KiB. Require exact approved `Origin`, same-origin `Sec-Fetch-Site`, CSRF validation, HTTPS and `Cache-Control: no-store`. Apply reviewed per-candidate and per-client-IP limits, including failed password attempts. Do not expose this endpoint as the extension's credential surface.
2. The BFF must resolve a current HttpOnly/Secure/SameSite server-held web session through the independent authentication-session repository. It may use existing bearer authentication for candidate lookup, but must not infer recent authentication, account binding, session ID or generation from the numeric bearer `sub`. Resolve the current `CandidateWebSession` internally; the browser cannot supply these fields.
3. Generate the candidate challenge through the existing pairing core only after resolving this current independent subject/session. Deliver the raw challenge nonce through the web page's protected response/body; never a URL, redirect, analytics event or extension message. The displayed confirmation must identify the exact device/key/request or revocation target. Do not enable challenge creation using a client-supplied `subject_uuid` or `session_id`.
4. Accept this exact body, with `operation` limited to `confirm_pairing` or `revoke_device`:

   ```json
   {
     "protocol_version": 2,
     "operation": "confirm_pairing",
     "method": "password_reauth",
     "challenge_id": "<canonical UUID>",
     "nonce": "<canonical UUID returned by the exact challenge>",
     "password": "<candidate's exact password, never persisted>",
     "confirmed": true
   }
   ```

5. Call `PasswordReauthService.execute(trusted_context, raw_body)` with the reviewed independent repository, production candidate signer and trusted native dispatch port wired server-side. The service's strict validation must run behind a sanitized HTTP exception mapper. Do not serialize Pydantic validation inputs, raw request bodies, upstream exceptions, passwords or hashes in logs, traces or 422 responses. No client may select a signer, dispatch adapter, issuer, identity context or coordinator plan.
6. A confirmed pairing returns only `pairing_id`, `device_id`, `status: CANDIDATE_CONFIRMED`; revocation returns `device_id`, `status: REVOKED`, `event_sequence`. Map `GuardDenied` uniformly to 401 with the fixed failure label and `GuardUnavailable` to 503 with the fixed unavailable label. Size/invalid-JSON transport failures may use generic 413/400 without echoed values. No signed candidate assertion, bearer or password reaches the extension.
7. Never retry a dispatched mutation automatically on a timeout/503. Use an independently owner-checked, redacted status surface and durable invocation reconciliation. Unknown state grants no permission to sign/mutate again. Device completion still requires its separate key-possession challenge and short-lived identity-only claim. Neither candidate confirmation nor a device claim can authorize filling/submitting an employer application.

Actual BFF/HTTP/CSRF/rate-limit integration, current session lifecycle/provisioning, production KMS wiring/IAM, native invocation and restore completeness, and provider recent-authentication are separate enablement gates. This stage is backend service evidence only, not real-browser, real-provider, real-cloud retention or employer-portal proof.

## Local proof

At this stage the dedicated suite has 71 behavioral/fault/ownership cases; together with the unchanged existing pairing-service, crypto and process suites, 199 cases passed with no skips. Scoped Ruff and Mypy passed for the new service and test. Cases include actual password verification, changed hashes behind a cached authenticated SQL `User`, missing/Google-only users, exact whitespace preservation, canonical/bounded secret validation, forbidden client privilege fields, registered/current lifetime and web-session ownership, account tombstone rejection despite surviving SQL credentials, challenge/operation/nonce/epoch/expiry mismatch, cross-subject pairing and cross-owner device revocation, revocation during signing, concurrent same-challenge signing, signer/error sanitization, capped near-expiry assertions, unavailable authority without retries and confirmed commit followed by lost response. Dispatch-port cases verify the frozen canonical server context carries no credential material, extra assertion-bearing or wrong-target responses are rejected, and unknown dispatch never retries. Synthetic signing keys exist only in tests and are explicitly injected.

The original scalar-reader patch was held after an independent review reproduced hash exposure through SQLAlchemy DEBUG row logging. The superseding native-reader tests cover enabled engine DEBUG/echo, enabling DEBUG during the actual query, cursor cleanup on faults, read-only connections, invalid wait budgets and oversized stored hashes. Three cases use actual disposable localhost PostgreSQL 17 databases and pinned psycopg: correct/wrong/missing-password reads under DEBUG and mid-query logger activation, exact native timeout settings, and an actual table-lock timeout with connection release. PostgreSQL dialect initialization can log harmless server/schema rows; no credential hash or password is logged. Each PostgreSQL case creates and removes only its unique synthetic database. This is native-driver evidence, not production connection, TLS, cloud or retention proof. The earlier 184-case run remains historical; its held patch is superseded.

No main-worktree file, route, migration, deployment, live cloud/model/provider call or production configuration was changed by this isolated implementation.
