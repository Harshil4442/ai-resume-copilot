## Candidate journey

After explicit consent, the server issues a five-minute challenge bound to the same signed-in candidate, stable Google issuer/audience/subject principal and exact current SQL credential revision. The Google Identity Services popup returns a freshly signed ID token with that nonce. The backend verifies its signature, issuer, audience, verified email, stable subject and issuance window; email alone cannot link ownership. The candidate chooses a HireWiz password for separate sensitive-action approval. Existing password holders must also prove the current password. The existing user ID, profile, resumes and credits stay attached to that same account.

An existing password candidate can explicitly enroll using the current password. A new password signup uses the existing genuine native registration path once configured. Before external I/O, enrollment commits one PENDING attempt. Only the original definite native enrollment and protected activation acknowledgements can activate the exact same SQL credential revision. A lost acknowledgement remains pending; the UI offers inspection and never silently repeats enrollment or adopts a retained status.

Linked Google candidates continue ordinary Google sign-in using a distinct Google-authenticated native session. Its stable principal must equal the original enrollment principal; its token commitment is one-use and no raw token is retained. Password sessions retain their old canonical serialization. OAuth is never relabeled as password proof. Device pairing and final submit still use a separate current-password challenge. Linking a Google identity onto an already-protected password account with a different original random principal remains unsupported; email matching cannot perform that conversion.

The configured companion generates and retains its original non-extractable Chrome P-256 key. Connect opens `/browser-companion?pairing=<id>`, which now renders the actual pairing review. The candidate reviews the key and separately approves with the current password. Original native completion, original independently protected device activation, and exact SQL projection precede the signed identity claim. The SQL and native key digests remain distinct; submit bindings derive the native fingerprint from the verified public key. No per-user or device seed is needed.

The same retained browser key and native-assigned device ID then open application assistance. Every paired-cohort assistance request verifies its Chrome signature, releases SQL before native I/O, freshly checks independent protected activation/current ownership and execution epoch/policy/revocation, then reacquires current SQL ownership and credential locks. Status, a signed claim, restored SQL or a cached epoch cannot create authority.
