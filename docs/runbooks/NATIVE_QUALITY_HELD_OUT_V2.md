# Held-out native acquisition V2

This is a separately invoked evaluation component. It does not deploy the
customer application, create an IAM grant/Job, issue funding, accept a human
review, run a model, submit an employer application or authorize sales.

The component owns exactly eight Python package files: the two docstring-only
initializers and `engine.py`, `channel.py`, `job.py`, `qualification.py` and
`isolation.py`, plus the pure `bridge.py`. Its three test groups are `test_native_acquisition_v2_engine.py`,
`test_native_acquisition_v2_channel.py` (including Job controls), and
`test_native_acquisition_v2_source.py`. This runbook, lock/configuration files,
original proof helpers and the reused finite source dependencies are hash-bound.
The six public Courier Prime font/license/provenance source assets are bound
individually. This does not allow reading arbitrary evaluation cases or oracles.

The unchanged V1 dependency inventory remains a separate reference/compatibility
check, with no V2 runtime authority. It is not the V2 reached-import closure. Its
receipt, entry, Bundle, development prefix, permits and 80-request limit do not
qualify or authorize V2. No V1 gate is widened. New local imports must resolve
inside the declared closure; source-child imports must have the expected file
provenance. Additional package members or executable initializers refuse.

Image inputs, controller dependencies and proof inputs have explicit roles.
Image inputs are the bounded conservative transitive import closure of the
entry/engine/channel, initializers, image recipe/locks, six source assets and
exact literal data read by the engine. Conditional/function-local imports are
included; actual reached module origins are checked in the source child.
The operator's qualification/isolation/host-helper code is separately bound.
CI/tests/runbook and the V1 reference snapshot do not silently become image
runtime inputs. All eight package source files retain component binding.
The engine actually imports the bridge, so it is also in the reached image
closure. The final `evaluation/development40_transport_v2.py` entry is a single
explicit runtime **byte input**, never an imported or executed capture entry.
The original development40 qualification sibling is controller-only; only the
isolation module's explicit lazy import may reach it. A runtime import of either
that sibling or the entry byte input refuses.
An observed V1 reference refusal is metadata, never an exception to its unchanged
guards: fresh all-five CI must still pass the existing V1 tests.

The new source child uses the actual checkout's committed HEAD, App inventory,
schema contract, entry and full component/proof hashes. It has no credentials,
denies network/SQL, uses bounded read-only Git calls, and never executes a foreign
runner checkout. It does not select cases. The external read-only verifier then

Retained runner proof metadata is checked against that runner's actual source
and original CI/Build; it is never rewritten to current controller hashes.
Current controller CI independently covers its current proof inputs. A benign
proof/reference/host-only change with unchanged image/component inputs does not
by itself demand a new application image. Existing V1 guards remain unchanged.

Do not transplant an older App/release/CI/image tuple into this component. Finish
and commit integration, then qualify that actual source. Neither qualification
nor offline isolation output permits native processing by itself.

## Exact storage and request budgets

The Job accepts a raw Bundle at most2MiB, and populated native+authority inputs
plus the reserved Bundle at most2GiB. Native sources are each at most5MiB; the
manifest is at most256KiB. The complete authority closure has separate per-kind
counts/sizes. Those per-file ceilings cannot all be consumed simultaneously.
The v3 additions have their own finite kinds: `transport_job` allows nine files
of at most256KiB, and `transport_origin` allows one of at most256KiB, at most
2.5MiB combined. They share the existing2048 authority-object cap,1837 common
objects,1903 total input objects and2GiB union. Existing sixteen kinds and the
32-control cap are unchanged. No ten-file allowance is added to those global
ceilings. If complete evidence cannot fit, preparation must refuse; no artifact
omission or larger unreviewed budget is permitted.

The operator's input catalog additionally binds a global union of immutable
common generation references and fixed batch slots. It reserves all33 review
slots (256KiB each) and33 raw Bundle slots (2MiB each), a total74.25MiB, before
uploads. Common input bytes plus that reservation must fit2GiB. Current dispatch
reviews are separate from the common closure; common files use stable
`input.common.NNNN` names, and reviews/Bundles use fixed `input.review.XX.json`
and `input.bundle.XX.json` names. At most1837 common inputs plus66 batch slots
gives1903 distinct input objects. Exact common refs must be reused; alternate
names, replaced generations or dropping an uncertain slot refuse. This includes
all mirror bytes and all33 Bundles/review generations. A lost write ACK retains
its full slot reservation and does not authorize another create.

These pure catalog checks are not an upload implementation or an
administrator-proof invoice cap. Native preparation must actually use the
finite create-only naming/accounting contract. Without that enforcement the
conservative experiment retention quote remains up to66GiB input, not2GiB.

Output has its separate exact1814-object,2GiB envelope. Every phase and parent
batch claim/context/terminal is counted. First1 +31x10 +final9 =320 maximum
native HTTP sends in at most33 tasks:160 source inspections,80 TeX compilations,
80 compiled-PDF inspections. Refusals can stop a case; an UNKNOWN intent never
permits replay or expense release. Fresh directories, replicas, lost ACKs,
timeouts and partial restores do not reset the global claims.

Stored union bytes and repeated reads are different costs. Inputs can be
downloaded up to33x2GiB=66GiB. Conservative repeated output payload reads are up
to198GiB plus at most1089MiB historical-chain metadata. No value here promises
that missing vendor charges are zero. The complete quote and existing funding
review must cover runner, native sends, operations, reads, retention, networking
and logs. There is no funding request in this source preparation.

## Blocking scanner-rotation restriction

The frozen engine currently requires the historical development inspector and
compiler full URL/image/policy bindings to equal the current authorization. It
also binds the historical runner App digest to the currently shipped App
contract. A daily definitions image change therefore blocks lock reuse before
held-out selection, even though historical captures remain valid evidence of
their original time. Scanner definitions have a3-day maximum age; daily refresh
cadence and alerts24h before expiry are different constraints. Historical
quality evidence is not permission to process new files with expired definitions.

This is a blocking native-quality usability gap. The pure definitions-only
bridge is now the eighth source/proof member, but it carries no native authority.
A v3 lock may identify a bounded pending bridge request; parsing any such request
deterministically refuses **before any case selection** with
`definitions_bridge_native60_current_serving_receipt_unavailable`, even when
plausible receipt references are present. A genuine future Native60 producer,
its current-serving verification and explicit source integration are not
implemented by this slice. Future scope keeps the same approved App
contract/entry, native compiler, parser/runtime/fonts/policy, preserves genuine
original raw proof, verifies a genuine current derivative Build/source/parent
chain and fresh native acceptance, budgets the additional rescans in the whole
permit, and proves every original extraction/reading-order/rendered page
equivalent or requires review again. There is no generic old/new-image waiver
or cross-App equivalence here. A changed App contract remains an intentional
requalification/review restriction. The pilot App deployment is independent;
paid quality eligibility depends on resolving and proving this bridge.
