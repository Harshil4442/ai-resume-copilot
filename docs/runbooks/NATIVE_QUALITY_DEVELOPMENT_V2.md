# Development40 transport successor

This is a separately versioned GCS entry and source/isolation adapter. It is not
a dispatcher, funding grant, native acceptance, retail qualification or evidence
that a new image exists. Current C6 pilot deployment remains separate. Its image
does not contain this new entry and must never be relabeled as doing so.

`backend/evaluation/development40_transport_v2.py` supplies a store to the unchanged
V1 `run` seam. The original V1 main, Bundle, channel, semantic entry hash and all
old receipts remain unchanged. No held-out V2 entry, namespace, authorization,
permit, development lock or engine is imported by this runtime.

Both new executable modules live in the separate `backend/evaluation` namespace.
They add no package initializer and do not enter the historical V1 code roots.
The unchanged V1 source checker must still pass its original 464-file inventory;
no new entry or dependency exception is added to that checker.

## Transport and limits

The exact native command is isolated Python with the direct image script:
`/app/backend/.venv/bin/python -I -B /app/backend/evaluation/development40_transport_v2.py`.
The versioned adapter renders the remaining original namespace, exact bundle
generation/hash and private workspace arguments. It requires one task, first
attempt, zero Job retries and the original development evaluator/network,
resources and batch timeouts. The sole explicit environment addition is
`DISABLE_GCS_PYTHON_CLIENT_OTEL_BUCKET_METADATA=true`.

The entry rejects credential, endpoint, proxy, metadata, Python import, loader
and tracing overrides before constructing the SDK or fetching the bundle. Its
credentials and client both pin `googleapis.com`, and the client explicitly pins
`https://storage.googleapis.com`. Separate auth/storage sessions disable proxy
environment, redirects, HTTP adapter retries and unauthorized-response replay.
The original object port retains `retry=None`, generation-matched fetches,
create-if-generation-zero, object/byte limits and unknown-acknowledgment errors.

Each factory instance allows at most **two** metadata sends for the original
account-info and token GETs. It checks a ten-second observed elapsed budget
before and after each request and configures each request timeout to at most
five seconds and the remaining allowance. Failed statuses and transport errors
become a safe ValueError before google-auth's independent retry/backoff loop can
repeat them. Further credential refresh refuses rather than resetting a budget.
Configured requests timeouts are inactivity limits, not a hard whole-refresh
wall deadline. The original native Job timeout remains the external time bound.
This budget concerns the GCS credential factory, not the unchanged worker
transport's separate identity-token acquisition or the eighty service requests.
Every construction/fetch/run/error path closes the owned client and sessions.

## Source and native qualification

The finite new identity binds its four component files, the committed current
code/dependency inventory, Git tree, original semantic/channel hashes, actual
proof source, Dockerfile, lock and CI command bytes. It is distinct from V1's
historical dependency inventory. A source child uses the unchanged low-level
SourceGuard to check all target tracked bytes against its actual commit; target
source is data and is never imported or executed. Trusted local imports must be
in the declared source inventory. Dirty, foreign, linked or shadowed source
refuses. No historical receipt/fingerprint or broad source exemption is adopted.

Before local child imports, a bounded Git metadata read verifies and loads only
the unchanged trusted-root C6 controller helper at its exact pinned hash, then
installs its existing I/O-denial controls. An exec-origin/source-byte fence
already protects that loading interval. The child requires isolated Python,
disabled bytecode writes and an empty private `-X pycache_prefix` so valid ignored
bytecode cannot replace the checked source. Ignored namespace shadows cannot
execute before refusal. A later legitimate change to that bootstrap helper
requires an explicit reviewed successor pin in this new component; there is no
silent fallback or reuse of an old receipt for changed helper bytes.

Future `verify_qualified_runner` requires actual source-child identity, the
schema26 application compatibility fingerprint, genuine exact-source five-job
CI and its three mandatory backend qualification steps, a successful native
Git-source Build and exact immutable image, and retained canonical CI/Build metadata
hashes. It also checks the actual controller HEAD's CI and rechecks both roots
after observation. Original neutral source/Git/CI/Build helpers are reused;
original V1 runner/entry acceptance is not widened. Source identity by itself
does not prove an image, issue a permit or release an expense hold.

Owned regression tests run under the existing full backend test command and
exercise the actual locked SDK with fake adapters/dummy credentials, real
credential metadata parsing using owned responses, source-child/receipt/Job
negatives and original store-injection delegation. They must not read the
actual evaluation corpus, selection, native captures or reviewer outputs.
Fake responses, local hashes and authored tests are never native acceptance.

After source review and genuine fresh CI/Build, native use still needs separately
reviewed development40 funding for eighty service attempts, exact object prefix,
evaluator IAM, genuine fresh inspector/compiler acceptance, actual Job/Execution
provenance and the original generation-bound journal/once-claim rules. All nine
batch limits remain `1 + 7×10 + 9`. Unknown object, native request, Job, claim or
acknowledgment outcomes retain their original intent, expense and journal;
read-only reconciliation cannot authorize a resend or fresh-directory escape.

The frozen held-out V2 development-lock consumer expects original V1 runner and
execution arguments. A future capture through this new entry cannot be relabeled
as that old native40 receipt. A separate reviewed lock-consumer successor is
required before using such captures in a held-out workflow. No held-out320 permit
or historical native receipt is transferred here, and the conditional SDK audit
does not fabricate a claim that earlier real requests were repeated.
